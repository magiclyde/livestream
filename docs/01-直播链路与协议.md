# 直播链路与协议选型

## 1. 一条直播流的完整链路

任何直播系统都遵循大致相同的流水线：

```
采集 → 前处理 → 编码 → 传输/分发 → 播放
```

| 环节 | 做什么 | 常见实现 |
|---|---|---|
| 采集 Capture | 拿到摄像头/麦克风/屏幕的原始数据 | 浏览器 `getUserMedia`、OBS 设备采集 |
| 前处理 | 美颜、降噪、裁剪、水印、分辨率调整 | 滤镜框架、WebGL、WebCodecs 处理 |
| 编码 Encode | 把原始图像/音频压缩成标准格式 | 视频 H.264 / VP8 / VP9 / AV1；音频 Opus / AAC。浏览器内置编码器，OBS 用 x264 |
| 传输/分发 | 决定数据以什么协议、走什么通道到达服务器和观众 | RTMP / HLS / WebRTC / SRT / RTSP |
| 媒体服务器 | 收流、转发、转码、录制 | nginx-rtmp、MediaMTX、livego、自研 SFU |
| 播放 | 解码并渲染 | `<video>`、hls.js、flv.js、播放器 App |

## 2. 常见传输协议对比

| 协议 | 传输层 | 典型延迟 | 特点 | 典型用途 |
|---|---|---|---|---|
| RTMP | TCP | 2~5s | Adobe 老协议，推流端事实标准，OBS 默认推流用它 | 推流上云 |
| HLS | HTTP (TCP) | 5~30s | 把视频切成 `.ts`/`.m4s` 分片 + `m3u8` 索引，兼容性好、好缓存 | 点播/直播分发 |
| WebRTC | UDP (SRTP) | <1s | 浏览器原生支持，双向实时，需要信令 + ICE 协商 | 视频会议、低延迟直播 |
| SRT | UDP | <1s | 自带丢包重传，抗弱网 | 专业推流 |
| RTSP | TCP/UDP | 亚秒级 | 安防/摄像头行业标准 | 监控流接入 |

一句话总结：**RTMP 负责"推上去"，HLS 负责"发出去"，WebRTC 负责"实时聊"**。
传统直播链路是 推流 RTMP → 服务器转封装成 HLS → 观众用 hls.js 播放；
实时互动链路是 浏览器 → WebRTC（UDP）→ SFU 转发 → 浏览器。

## 3. 为什么本项目选 WebRTC + Go SFU

- 纯 Go 就能实现媒体服务（Pion 库），不需要 ffmpeg / nginx-rtmp / MediaMTX 等外部进程；
- 延迟低、链路直观：浏览器 → RTP → Go 服务 → RTP → 浏览器；
- WebRTC 里的 SDP、ICE、DTLS、SRTP 是音视频方向的高频考点，值得亲手写一遍；
- 浏览器原生支持采集和播放，前端代码量小。

## 4. 本项目链路（v1 实现目标）

```
[主播浏览器]
  getUserMedia 采集音视频
  WebRTC 编码（浏览器内置）→ SRTP/UDP
        │
        ▼
[Go SFU 服务]（本项目）
  WebSocket 信令：join / offer / answer / ice
  房间管理：每房间 1 主播 + N 观众
  收到主播 RTP 包 → 不转码，原包转发给每个观众的 PeerConnection
        │
        ▼
[观众浏览器]
  RTCPeerConnection 收流 → <video> 渲染
```

## 5. v1 边界（本期不做，后续可扩展）

- 不转码：观众看到与主播一致的码率/编码（这是 SFU 的特性，而非缺陷）；
- 不录制、不做 HLS：后续可加 ffmpeg 录制，或 WebRTC→HLS 网关；
- 不做鉴权、不做房间列表持久化：输入房间号即加入，纯学习用途。
